# 双向剪贴板的系统接入口核查

日期：2026-11-09。结论范围：当前 CH32 双设备桥、已恢复源码及下列公开接口。目标未完成；本记录不替代端到端验收。

## 有效要求

- 双向文字、图片、文件、多文件、文件夹，正常 ⌘C/⌘V，要求快速。
- 图片和文件正文走有线 Bulk；保留键鼠、多指手势、自动边缘返回和两机本机剪贴板。
- mini 不安装、也不临时运行本项目程序或脚本。不得通过 HID 命令绕过；不使用 macOS 共享、Wi-Fi、蓝牙。
- 保留当前已验收输入版本，不为验证剪贴板中断控制。

“不安装”与“不运行”是两个不同条件。当前 AGENTS.md 和用户最近明确指令同时要求两者。不能自动恢复此前已撤销的便携程序许可。

## 当前源码证据

1. `firmware/ch32v407/descriptors.c` 的 clipboard 报告使用厂商自定义 Usage Page `0xff60`。它是64字节私有消息，不是系统通用剪贴板数据类型；文件接口是独立 CDC/Bulk。
2. `firmware/ch32v407/bridge.c` 的 `admitted()` 要求两个相同非零 stream_session，且当前事务得到接收侧 grant。仅 Book 发送数据不会自动形成目标接收程序或文件。
3. `host/clipboard/WKClipboardContent.swift` 的 `snapshot()`、`apply()` 等通过 NSPasteboard 读取系统剪贴板、写入文字/图片或本地文件URL。调用发生在运行该代码的电脑上；Book 的对象不会指向 mini 的剪贴板。
4. `WKOnDemandClipboard.swift` 把该对象、传输层和会话组成 WKCompanion。`WKStreamFiles.swift` 提供正文、校验及文件流，不能独自替代目标系统接入口。
5. 固件主循环将输入与文件分开，并有界推进 Bulk。此前混合负载模拟通过，只证明调度；不证明零运行条件下的系统剪贴板功能。

## 新增实际桥接诊断

`results/clipboard-zero-runtime-20261109/admission_probe.c` 直接链接当前 bridge.c 与 wire_protocol.c；不打开 USB、串口、系统剪贴板，不启动目标程序。

| 条件 | 结果 |
| --- | --- |
| 两个USB逻辑端在线，仅Book声明会话 | 目标方向正文准入0个单元 |
| 两端声明会话，但无接收侧grant | 正文准入0个单元 |
| 诊断明确模拟两端会话及各自接收grant | 两个方向各准入1个单元 |

完整输出、构建日志及源码哈希保存在同目录。模拟grant不是运行中的mini已经支持该协议，也不是文件成功落盘。本诊断确认当前协议确实需要接收端参与；不能通过增加缓冲或提高速率消除该依赖。

## 官方资料核查

- Apple 的 [NSPasteboard 文档](https://developer.apple.com/documentation/appkit/nspasteboard) 将其定义为应用与剪贴板服务交互的对象，列出本地读取、写入和数据类型接口。它没有在本次核查中给出外部USB设备访问通用剪贴板的入口。此为接口核查结果，不宣称穷尽全部未公开接口。
- [USB-IF HID资料](https://www.usb.org/hid) 说明Usage用于描述报告字段，并明确新Usage不意味着主机支持。因而给私有报告命名为clipboard，或添加Copy/Paste操作，不能证明macOS会传回系统内容。
- [Apple Universal Clipboard要求](https://support.apple.com/en-us/102430) 包括同一Apple账户、Bluetooth、Wi-Fi和Handoff。不满足本项目的纯有线、无共享约束，未启用它。
- j5create [JUC400商品页](https://en.j5create.com/products/juc400) 宣传免安装；其[官方手册](https://j5create.com/download_new/manual/juc400.pdf)第3—4页要求打开线内Wormhole入口，第8页说明两端工具程序和插线驻留选项。这个具体产品证明“免安装”可以仍有运行程序，不能作为“零目标程序也能读取剪贴板”的证据。该手册面向旧版Mac OS，只用于分析其实现条件，不据此承诺当前系统兼容性。

据此作出的架构判断：在已核查接口和当前代码中，没有可交付的零目标运行系统剪贴板入口。Bulk本体不是当前缺失功能的解决方案。未使用隐藏安装、共享或Shell启动来替代用户要求。

## 后续门槛

继续集成前，必须找到一个有macOS实际支持证据、能读写目标系统剪贴板且满足零运行约束的接入口；或由用户明确修改零运行条件。现有商业线内程序、交换盘手动中转、单向模拟打字都不能作为完整目标的替代交付。

目前没有这个接入口；目标保持未完成。重复刷新已工作的手势固件或增加同类模拟压力轮次，不会解决该系统边界。


## 最新明确：程序只能由硬件执行

用户重新启用目标并补充“只能由硬件运行程序”。这确认禁止在mini执行便携程序；存储位置在线内不等于执行位置在板上。此前便携程序建议不再作为待授权方案。

本轮再次核对上述源码哈希，全部未变；没有新的系统剪贴板接入口。当前板载固件能执行协议与数据转发，但NSPasteboard的读写调用依赖运行在目标macOS中的调用者。不能把该调用移动到CH32后仍认为它能访问mini本地剪贴板。

以程序的执行位置筛选后：

| 候选机制 | 满足本次完整目标？ |
| --- | --- |
| 板载HID/触点固件 | 已解决输入；没有目标剪贴板正文读写路径 |
| 板载Bulk桥 | 提供传输；仍需操作系统侧的内容生产者与消费者 |
| 线内便携应用、浏览器JS、Shell启动 | 代码仍由mini执行，违反当前限制 |
| MSC文件中转 | 不等于通用系统剪贴板的双向原生⌘C/⌘V，不能替代完整目标 |
| 仅增加Flash、PSRAM或更强板载处理器 | 不会自动给mini增加系统剪贴板协议支持 |

[Arm官方USB通信说明](https://arm-software.github.io/MDK-Middleware/main/USB/USB_Concepts.html)描述了主机发起传输、主机客户端缓冲区与设备端点之间的关系。这支持“端点数据需要主机消费者”的总线模型，不独自证明全部系统接口不存在。结合当前厂商Usage、私有会话/grant协议和NSPasteboard调用，本轮仍没有可验证的纯硬件完整剪贴板路径。

后续真正的解锁条件是出现符合现有限制、并有实际系统支持证据的接入口。不能继续用重复刷板、同类吞吐模拟或要求用户反复改回便携程序来代替这个条件。保留文字、图片、多文件与目录、速度、取消和输入共存的完整目标，不按较小功能宣告完成。
