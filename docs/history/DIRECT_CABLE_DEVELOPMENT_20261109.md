# 线内便携候选开发记录

用户最新选择允许 mini 执行线内程序，但不安装、不设置持久服务。开始改功能前，原代码与 README 已提交为 `7f09bef` 并推送到公开仓库 `KevinCJM/WiredKVM`。

本批候选没有刷板、退出当前控制器、改变自动服务或执行 mini 命令。Book 只读重新发现 `1a86:4070` 的控制口；调试器当前没有连接。

## 修正的问题

- 便携发现仍仅匹配旧目标身份 `1a86:4071`。增加当前 native-v2 的 `05ac:0265`，同时约束私有 usage、厂家、原型序列号及接口，避免匹配普通 Apple 妙控板。
- `WK_TREE` 未链接到便携构建，且启用后发现 Finder 树目录分支的条件编译语法错误。修正并链接 Rust 树引擎。
- 便携组件原先会开启旧滚动/手势注入。关闭该路径，保留已验收的硬件 native-v2 输入。
- 原生控制 CLI 排斥触点与剪贴板同时运行。仅放开有界剪贴板通道，继续排除交换盘与旧安装盘自动化。
- 包装工具会生成空 FinderInfo。源应用验签通过不足以证明盘内可启动；只清理新镜像内该属性，再重新只读挂载验签。
- 新启动上传不能受普通文件桥“两端在线”的条件限制；已发布的程序镜像不能在运行时覆盖。
- RAM 程序上传和剪贴板文件引擎必须按顺序交接独立 CDC，且使用独占文件锁。
- 捕获器就绪后才装载程序盘，装载失败保留输入；组件启动失败不能删除控制器仍绑定的私有 socket 目录。
- 自检新增的目录比较最初按 URL 表示比较，因尾部分隔符不同触发断言；用文件路径比较后通过。
- Cargo 只经 rustc 临时追加 staticlib 会向新依赖传 rmeta，导致链接失败。改成独立生成的 staticlib wrapper，保留旧 MT2 crate 的构建方式。

## 第一轮实机：输入通过，PSRAM 上传失败

`e23dfff` 候选已推送后，在指定 `0x46740011` / UID `ad21ad506c54c6c6` 上刷入 `dde0403e...`，完整 576 KiB 备份与独立读回通过。用户确认键鼠、双指、四指和自动返回全部正常。

独立 CDC 上传完整 3,405,824 字节镜像时返回 `Code::Storage`；未发布半成品，原输入继续可用。原始证据在 `results/portable-direct-cable-20261109/hardware/`。这说明启动时的少量字节探测不能代表真实连续上传；此前主循环模拟用 memcpy 代替 PSRAM，也不覆盖真实内存适配层。

诊断候选 `candidate-ram-setup-20261109-diag-v2` 使用显式总线屏障、对齐字读写及“每次写清读 FIFO”策略；WCH 文档本身支持 8/16/32 位访问，不能将此故障解释为“不支持字节”。根因仍需实机故障数据确认。候选增加连续 512 字节、476 字节相邻边界、1 KiB 跨页及 4 MiB 范围的启动探测；固定只读状态返回首个失败字节、预期/实际值、模式/控制寄存器和已校验块数。

新适配层模型覆盖写缓冲顺序、读 FIFO、部分字/边界、故障闭锁与超时；Rust 核心保留失败会话和偏移但仍立即废弃半成品。装载器处理完已发送的最多 16 格窗口，再读取诊断，防止剩余确认污染下一次请求。新增测试及真实主循环交错 1000 轮模拟通过，均不等于物理 PSRAM 通过。


## 第二轮诊断与遗漏的供电前置条件

诊断修正版 `0d3a5fff...` 已刷写并独立读回；完整上传再次失败，首个失败字节为 5173，预期 95 (`0x5f`)、实际 93 (`0x5d`)，该格起点 4760。诊断寄存器和日志在 `hardware-ram-diag-v2/`；未发布程序盘。这证明仅增加屏障/字访问/FIFO 策略不足，不能把这些改动说成已解决根因。

核对官方完整示例 main()，发现它先调用 `PWR_VDD18LevelConfig(PWR_VDD18_Level1)` 再进入 PSRAM_INIT；前两版只对照初始化函数，遗漏了这一前置条件。供电修正版 `candidate-ram-setup-20261109-power-v3` 补齐这一调用，保留原 USB 和系统时钟；只读状态第 16 字在版本 2 中改为 EXTEN 配置，能确认供电档位实际写入。其固件 84,360 字节，SHA-256 `28c576763fe4f8a3588705945c4f53e5bf7be0a61c03fe9f51b205d7f2178f93`；已备份、刷写并独立读回一致，仍需完整物理上传确认效果。


## 第三轮物理通过与当前文件入口阻塞

补齐供电档位后，完整 3,405,824 字节程序镜像在 8.273 秒完成；Book 实际只读挂载的应用 SHA-256 与构建一致，完整应用读取与严格签名校验合计 0.446 秒。证据在 `hardware-ram-power-v3/`。这是补齐前置条件后的通过结果，未测量电压，不能延伸成开发板电气合格或大文件性能验收。

用户在 mini 看见程序盘，直接打开卷内应用并出现 ⇄。Book 临时换到 `portable-book-20261109-ram-power-v4` 协调器，保留原捕获器和触点 helper；原 LaunchAgent 暂时 bootout、配置未改，恢复入口仍在原 plist。第一次切换前检查因 macOS ps comm 固定截断到 15 字符而拒绝，未停止旧服务；改用已有 libproc 身份函数精确核对完整路径和进程创建时间后切换成功。

用户保持 ToDesk 退出，确认两台内部新文字复制粘贴、两个方向的新文字跨机粘贴均正常；键鼠、双指、四指和自动边缘返回也全部正常。当前 Book 文件入口报不可用，图片/文件/文件夹、大文件输入时延、取消与登录自启升级尚未实机通过；不得把文字成功扩大为完整交付。


## 文件入口修复、诊断版与首个内容校验

Book 文件入口失败已定位到目录别名：挂载后的 URL 规范化不保证得到内核挂载记录中的 `/private/var`；先在挂载前 realpath 固定目录，隔离挂载测得入口可用，约 1.398 秒。补充路径别名、只读入口、延迟 GET、内容完整性和取消回归。程序盘更新前曾有一次自动审批拒绝，原因是 mini 正从该来源卷运行；没有执行被拒操作。用户随后明确允许更新，并确认 mini 退出、两端推出后才冷重连上传 v5，未隐蔽替换活动来源卷。

新的 Rust 监督器支持可选 portable_host/portable_runtime，保留旧三进程模式。Book v5/v6/v8 临时试运行保留原 capture 和冻结的触点 helper；原 LaunchAgent 配置和二进制未改。新版不是已安装的登录自启服务。主控 ready 必须来自输入捕获；程序盘上传缺失/失败保留输入，不再把整个启动预检与程序盘可用性绑定。

用户确认 Book→mini 8 MiB 文件出现并有进度，输入正常；但第一次 mini→Book 出现 Finder 100004，Book 文件只有 0 字节。之前“看到文件即成功”的判断已撤回，失败文件保留为证据。Book v8 诊断版增加实际 Bulk 接收全过程、完成 SHA 校验及有界错误码，修正“元数据 READY 即传输完成”的状态文字；不记录剪贴板正文或个人文件路径。

v8 重试 mini→Book，日志从 REQUEST/START 到完整接收约 10.303 秒。Book 源文件与返回文件大小都是 8,388,608 字节、SHA-256 都是 `1b56cc59b9da209542f3bda071bb65f1bddca2c7ee9f5aeac90e4cd7b5716b4e`。这确认一次真实往返内容一致；不能据此确认高吞吐、所有文件类型或偶发错误已根治。原 100004 的根因仍未知。未读取 mini 终端、目标文件哈希或个人文件。

v7 回归期间修改过构建输入，导致结束时记录的源码哈希不能证明实际编译输入；该批证据已标记 INVALIDATED，未部署。构建工具/回归入口改为开始时快照并在结束时复核源码，v8 以冻结源码重新完整运行通过。不能边修改输入边生成“对应当前源码”的构建或测试证据。
